# Registry write gate — design, testing, verification

Depth for section 3 and 7 of SKILL.md. Load when changing the gate, debugging a
false block, or proving a hook edit actually took effect.

## What it is

`pre_tool_call` vetoes raw writes to the files `infra_upsert` owns, so the KB stays
open to change but has exactly one writer. A hand-edit skips frontmatter merging,
the `INDEX.md` refresh, the change-log entry and the `verified_at` bump; the node
table then describes files that no longer match it, and drift detection reports
the *hosts* as wrong when the *docs* were the thing edited behind its back.

Config: `registry_write_gate: block | warn | off` (default `block`), separate from
`guardrail_mode` on purpose.

## Covered vs deliberately open

| Covered (blocked) | Open (hand-editable) |
|---|---|
| `services/*.md`, `servers/*.md`, `projects/*.md` | `plans/`, `conventions.md` |
| `INDEX.md`, `change-log.md` | `LIVE-STATE.md` (generated by a watchdog script) |
| via `write_file`, `patch`, `sed -i`, `tee`, `cat >`, `mv`, `rm`, inline `open(…,'w')` | tracker files + their log dirs (a cron job writes them) |

Before widening coverage, check whether a script or cron job writes that path.
`LIVE-STATE.md` and the channel tracker are both machine-written; gating them
breaks a scheduled job to protect nothing.

## Test command

The suite imports `hermes_cli` and `plugins.plugin_storage`, so it needs a Hermes
checkout on `PYTHONPATH` (the repo's CI documents this instead of faking it):

```bash
cd ~/dev/dawgsec/infra-atlas
PYTHONPATH=<hermes-workspace> python3 -m pytest tests/test_registry_write_gate.py -q
```

Run the *whole* `tests/` dir too — the gate sits in the same hook as the
read-before-touch guardrail, and an early-return mistake shows up as guardrail
tests failing rather than gate tests.

## Verifying against the live registry

Do not trust a same-session probe: the plugin is imported once per process, so the
session that edited `hooks.py` keeps running the old code. Write a small script
that loads the plugin the way Hermes does (`_harness.load_plugin()`), points it at
the real registry root, and calls `on_pre_tool_call` directly — no writes happen,
so it is safe on production. Assert both directions: the covered paths block, and
the open paths + `infra_upsert` itself still pass. A gate that blocks everything
is as broken as one that blocks nothing.

Then apply it to the running gateway (`reload_running_gateway()` triggers plugin
re-discovery; callbacks already wired into platform adapters outlive a reload, so
a gateway restart is the clean apply).

## Pitfalls

- **Order matters.** The veto must precede the `guardrail_mode == "off"` return,
  or turning off the host guardrail disables the write gate too.
- **Symlink aliases escape the shell matcher.** `write_file`/`patch` are
  realpath'd and caught; `sed -i`/`tee` compare literal prefixes and are not.
  Realpath every candidate before matching.
- **Prose-only enforcement does not hold.** Skills that say "update the entry,
  add a change-log line" are what teach agents to hand-edit. Fix the code first,
  then the skill text — and check whether the offending skills are user-locked
  before planning edits to them.
- **A runbook can only grow through `infra_upsert`.** `upsert_entry` refuses a
  body shorter than the existing one, so a genuine structural rewrite has no
  sanctioned path. Give the tool an explicit `replace_body` before blocking
  rewrites, or agents will find a workaround that bypasses the audit trail.
